FP108 — Route the AI callers through the provider layer (engine, stage 2)
=============================================================================

What it does
------------
FP107 built one working provider layer; this milestone wires the
live AI callers to it. Five hand-rolled provider loops are gone:

- The chat hub (/api/chat) — via AIRequest.direct_messages, which
  passes the validated history through verbatim (the last message
  is not always from the user, so splitting history/user would
  have flipped roles). Temperature 0.7 preserved.
- The article question route (/api/ask_ai).
- The story intelligence drawer (/api/story_intelligence) — the
  >80-character check and deterministic fallback preserved.
- The RAMS drafter (rams_drafter.py) — max_tokens 2500 preserved.
- The receipt reader (receipt_reader.py) — via AIRequest
  .image_data_url, which makes the user message multimodal.
  OpenRouter-only chain: the vision model is OpenRouter-specific,
  so an OpenAI fallback with the same model name would fail.
  The route no longer passes the key; the provider layer reads it.

Changes underneath:
- core/ai/request.py: user defaults to "" (direct_messages
  callers need no dummy user string); new direct_messages and
  image_data_url fields.
- config/providers.json: OpenAI enabled (priority 3) — it is the
  live fallback everywhere, so the config now says so. Order:
  DeepSeek 1 (unconfigured, skipped), OpenRouter 2, OpenAI 3.
- The three FP107 providers now raise ProviderError on an empty
  reply (previously an empty reply counted as success, so the
  chat hub would not have fallen back the way it used to).
- Test doubles in the RAMS and receipt test files gained
  raise_for_status() (they now behave like real Responses), and
  the receipt tests use the new read_receipt(image) signature
  with the key from the environment.

Deliberate exception: /api/ai_brief keeps its own chain. Its
per-provider brief validation and reason-code diagnostics are
bespoke; forcing them through the manager would weaken the
diagnostics or complicate the manager for one caller.

Behaviour preserved (all covered by existing tests): the chat
hub's 503 "No AI provider is configured" message, reply +
provider name on success, the RAMS "no key" vs "unreachable"
messages, the receipt error messages, and the intelligence
deterministic fallback.
